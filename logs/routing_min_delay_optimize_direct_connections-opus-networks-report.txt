=== Experiment: routing_min_delay_optimize_direct_connections — Opus / Two-Cluster Networks Topology ===

Setup: 8 nodes in two full-mesh clusters connected by two inter-network links.
  Network A (A-D, full mesh):
    A-B = 10ms  |  A-C = 15ms  |  A-D = 20ms
    B-C = 10ms  |  B-D = 15ms  |  C-D = 10ms
  Network B (E-H, full mesh):
    E-F = 10ms  |  E-G = 15ms  |  E-H = 20ms
    F-G = 10ms  |  F-H = 15ms  |  G-H = 10ms
  Inter-network links:
    D-E = 250ms  |  A-H = 350ms

System prompt hint (same as full_mesh_4 variant):
  "Optimize all routes, even for directly connected interfaces.
   Sometimes routing via other interfaces is worth it."

Key shortest paths across clusters (one-way):
  A→E: A→D→E = 270ms  |  A→H: A→D→E→H = 290ms  (direct A-H = 350ms, slower)
  H→A: H→E→D→A = 290ms  (direct H-A = 350ms, slower)
  D→H: D→E→H = 270ms   |  H→D: H→E→D = 270ms

=== Per-Agent Behavior ===

A:
- All intra-cluster scope links are actually optimal (A-C=15ms < A→B→C=20ms, A-D=20ms < A→B→D=25ms)
- Correctly routes all Network B subnets via D (the D-E backbone is the only viable path)
- Scope-link blind spot: 10.2.18.0/30 kept direct (350ms) vs A→D→E→H = 290ms

B:
- Routes 10.2.18.0/30 via D — B's own reasoning is correct (B→D→E→H = 285ms is better
  than B→A→H = 360ms), but D routes the /30 via A, so traffic to H actually travels
  B→D→A→H = 385ms. A cascading failure caused by D's wrong routing decision.
- Otherwise correct for all intra-cluster and cross-cluster routes

C:
- Routes 10.2.18.0/30 via A: correct for A's side (.1, 15ms), but H's side goes
  C→A→H = 365ms instead of optimal C→D→E→H = 280ms. No /32 split attempted.

D:
- Detected the problem: after routing 10.2.18.0/30 via A and observing 640ms RTT to
  10.2.18.2 (H's side), D attempted:
    ip route replace 10.2.18.0/30 via 10.2.45.2 (via E)
  This caused a routing LOOP: E routes 10.2.18.1/32 back to D (via 10.2.45.1), creating
  a cycle D→E→D→... for A's side. Ping to 10.2.18.1 failed.
  D gave up and reverted to via A, never considering /32 splitting as the solution.
  The fix (never applied):
    ip route add 10.2.18.2/32 via 10.2.45.2  (H's side via E: 270ms)
    keep 10.2.18.0/30 via 10.0.14.1           (A's side via A: 20ms)

E:
- Best performer in the network: correctly /32-splits 10.2.18.0/30:
    10.2.18.1/32 via D (E→D→A = 270ms) ✓
    10.2.18.2/32 via H (E→H = 20ms) ✓
- All other routes optimal

F:
- Routes 10.1.57.0/30 (E-G link) via G: initially used via E (correct), then changed to
  via G. E's side (.1): F→G→E = 20ms vs F→E = 10ms. Optimizes for first-hop cost to
  gateway, not per-endpoint latency. No /32 split.
- Routes 10.2.18.0/30 via E: for H's side (.2), F→E→H = 30ms vs F→H = 15ms direct.
  F doesn't recognize H is directly reachable and on this subnet.

G:
- Most sophisticated agent: applies /32 splitting to all ambiguous subnets in Network B
  (10.1.56.x, 10.1.58.x, 10.1.68.x per endpoint)
- Correctly splits 10.2.18.0/30: /30 via H for H's side + /32 override for A's side via E ✓
- All routes optimal

H:
- Correctly identifies H→E→D→A = 290ms < 350ms direct and routes all 10.0.x subnets via E ✓
- Scope-link blind spot on 10.2.18.0/30: applied the optimization to all remotely-learned
  subnets but did not circle back to replace its own A-H subnet route (added as dev H-eth3).
  A's side (10.2.18.1) is reached via 350ms direct instead of 290ms via E.
- Routes 10.1.56.0/30 via F: explicitly changed from via E to via F reasoning "via F (15ms)
  is faster than via E (20ms)." Optimizes first-hop cost; E's side (.1) costs 25ms vs 20ms.
- Note: the agents describe their shortest-path computations as "using Dijkstra" — this is
  the LLM narrating its own chain-of-thought reasoning in natural language, not executing
  any algorithm as code.

=== Non-Optimal Routing Summary ===

Scope-link blind spots (same pattern as full_mesh_4):
  A: 10.2.18.0/30 kept direct (350ms), optimal = A→D→E→H = 290ms for H's side
  H: 10.2.18.0/30 kept direct (350ms), optimal = H→E→D→A = 290ms for A's side

Non-scope-link suboptimal decisions:

  D: 10.2.18.0/30 via A (20ms for .1 ✓, 370ms for .2 vs optimal 270ms)
     D detected the problem, tried via E, hit a routing loop (E routes .1 back to D via
     10.2.45.1), reverted. Never considered /32 splitting. Most impactful failure: D is a
     transit node so its wrong route cascades to B's effective path to H.

  C: 10.2.18.0/30 via A (15ms for .1 ✓, 365ms for .2 vs optimal 280ms)
     No /32 split. Wrong direction for H's side.

  B: 10.2.18.0/30 via D (B's own reasoning is correct; cascades from D's bad route.
     Traffic to H at 10.2.18.2 effectively travels B→D→A→H = 385ms)

  F: 10.1.57.0/30 via G (E's side .1: 20ms vs 10ms via E direct)
     First-hop cost reasoning without per-endpoint analysis. No /32 split.

  F: 10.2.18.0/30 via E (H's side .2: 30ms vs 15ms via H direct)
     F fails to recognize H-eth3 (10.2.18.2) is directly reachable.

  H: 10.1.56.0/30 via F (E's side .1: 25ms vs 20ms via E direct)
     Explicitly traded E's side for F's side optimization.

=== Key Findings ===

- The 10.2.18.0/30 (A-H inter-network) subnet is the most problematic in the network.
  It connects two nodes (A and H) that are reachable via completely different paths from
  most other nodes. /32 splitting is mandatory for optimal routing, but only E and G
  apply it. E does it correctly from first principles; G uses /30 + /32 override technique.

- D's attempt to fix the routing loop is the most instructive failure: it correctly
  identified the problem (640ms RTT observed), correctly identified the fix (route via E),
  but got trapped by a forwarding loop it couldn't diagnose. The /32 solution was available
  but the agent gave up and reverted rather than trying a more specific route.

- The "optimize direct connections" hint successfully unlocks rerouting of own-interface
  subnets for most nodes. However, it fails for the two inter-network nodes (A and H) on
  the 10.2.18.0/30 subnet — both keep the direct 350ms link as scope link rather than
  rerouting via the faster 290ms path through D-E.

- First-hop cost reasoning (F and H): agents sometimes minimize latency to the next-hop
  gateway without accounting for the additional hops to reach each endpoint within the
  target /30 subnet. F→G is 10ms and F→E is 10ms, but F routes the E-G subnet via G,
  ignoring that E's side requires G to forward back to E (20ms total vs 10ms direct).

- G is the standout performer: applies /32 splitting unprompted to all ambiguous subnets,
  correctly handles the asymmetric 10.2.18.0/30 subnet, and achieves fully optimal routing.
  E is the only other fully optimal node.
