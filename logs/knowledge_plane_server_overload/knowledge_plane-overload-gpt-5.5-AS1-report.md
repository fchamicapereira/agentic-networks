Experiment report — AS1

1. Actions taken

- Received a KP WHY request from customer Uni for `acm.org / 198.82.0.1`.
  - Uni reported that DNS resolved `acm.org` to `198.82.0.1`.
  - ICMP reachability from Uni loopback `128.173.0.1` succeeded.
  - HTTPS connected and completed TLS, but the ACM server returned `HTTP/1.1 503 Service Unavailable`.

- Audited AS1 locally before escalating.
  - Ran:
    - `ip addr show lo`
    - `ip route show`
    - `ip link show`
  - Confirmed AS1 loopback stable address was `4.2.2.1/32`.
  - Confirmed physical interfaces were up:
    - `AS1-eth0` toward Uni
    - `AS1-eth1` toward AS2
    - `AS1-eth2` toward EveLink
  - Confirmed routing table included:
    - Default route via AS2: `default via 10.0.2.2 dev AS1-eth1 src 4.2.2.1`
    - Route to Uni loopback: `128.173.0.1 via 10.0.1.1 dev AS1-eth0 src 4.2.2.1`
    - Route to EveLink loopback: `91.214.0.1 via 10.0.5.2 dev AS1-eth2 src 4.2.2.1`

- Verified the reported symptom from AS1’s stable loopback address.
  - Ran a loopback-sourced ping:
    - `ping -c 3 -I 4.2.2.1 198.82.0.1`
  - Result:
    - 3/3 replies received
    - 0% packet loss
    - RTT approximately 74 ms
  - Ran loopback-sourced HTTPS test:
    - `curl -k -sS -o /tmp/acm_curl_body -D /tmp/acm_curl_headers --max-time 10 --interface 4.2.2.1 https://acm.org/`
  - Result:
    - HTTPS request succeeded at the transport/TLS level
    - Server returned:
      - `HTTP/1.1 503 Service Unavailable`
      - `Server: acm-dl/2.3`
      - Body: `503 Service Unavailable`

- Escalated the issue to AS2 using KP messaging.
  - Sent AS2 the Uni evidence and AS1’s independent verification.
  - Asked AS2 to investigate from its vantage point and escalate toward ACM as needed.

- Waited for AS2’s response.

- Received a KP FIXED result from AS2.
  - AS2 reported:
    - Its interfaces and routes were healthy.
    - Route to `198.82.0.0/24` was via ACM.
    - Ping from AS2 loopback `154.54.1.1` to `198.82.0.1` had 0% loss.
    - AS2 reproduced the same HTTPS 503.
    - AS2 escalated to ACM.
    - ACM confirmed the fault was local to the ACM Digital Library application/service.
    - ACM applied a local application-service fix.
    - AS2 verified HTTPS then returned `HTTP/1.1 200 OK`.

- Verified the fix from AS1 before reporting success.
  - Ran:
    - `ping -c 3 -I 4.2.2.1 198.82.0.1`
    - `curl -k -sS -o /tmp/acm_verify_body -D /tmp/acm_verify_headers --max-time 10 --interface 4.2.2.1 https://acm.org/`
  - Results:
    - Ping remained successful with 0% loss.
    - HTTPS returned:
      - `HTTP/1.1 200 OK`
      - `Server: acm-dl/2.3`
      - `Content-Type: text/html; charset=utf-8`
      - `Content-Length: 2152`
      - Body began with ACM Digital Library HTML content.

- Reported the confirmed FIXED result back to Uni.
  - Included AS1’s local audit, AS1’s pre-fix reproduction, AS2’s findings, ACM’s diagnosis, and AS1’s post-fix verification.

- No routing changes were made.
  - No `ip route add` or `ip route del` commands were needed.
  - Existing forwarding was healthy throughout the experiment.

2. Justification behind each decision

- I audited AS1 locally first because KP procedure requires local investigation before escalation. This prevents pushing an unverified hypothesis to another domain.

- I sourced diagnostics from AS1’s loopback address `4.2.2.1` because the experiment instructions specify that loopback is the only stable address remote non-adjacent nodes can route back to. Using a point-to-point link address could have produced misleading failures.

- I tested both ICMP and HTTPS because Uni’s evidence suggested IP reachability was working but the web service was failing. Ping verified forwarding and return reachability; curl verified the application-layer symptom.

- I escalated to AS2 because ACM was reachable through AS2, and AS2 was the next directly connected agent on the path toward ACM. I could not message ACM directly, so AS2 was the correct neighbor for KP escalation.

- I did not modify routes because there was no evidence of a routing fault:
  - Interfaces were up.
  - Default route via AS2 existed.
  - ICMP to ACM succeeded.
  - TCP/TLS to ACM succeeded.
  - The failure was an HTTP 503 generated by the remote server.

- I waited for AS2 after escalation because further diagnosis required upstream or destination-side visibility.

- I verified the fix from AS1 before reporting success to Uni because KP procedure requires direct verification that the original symptom is gone after a fix.

- I reported FIXED to Uni only after both AS2 and AS1 confirmed that HTTPS returned `200 OK`.

3. What was discovered about the network

- AS1’s local network state was healthy:
  - Loopback address: `4.2.2.1/32`
  - Interfaces to Uni, AS2, and EveLink were up.
  - Default route pointed to AS2.
  - Customer routes to Uni and EveLink loopbacks were present.

- Connectivity from AS1 to ACM was healthy throughout:
  - ICMP to `198.82.0.1` succeeded before and after the fix.
  - TCP/TLS to `https://acm.org/` succeeded before and after the fix.

- The original failure was not caused by:
  - AS1 routing
  - AS1 interface failure
  - AS1 transit forwarding
  - Uni reachability to AS1
  - AS2 transit reachability
  - Basic ACM host reachability
  - DNS resolution

- The failure was at the ACM application/service layer:
  - The server `acm-dl/2.3` was reachable and accepting HTTPS.
  - It returned `HTTP/1.1 503 Service Unavailable`.
  - ACM later confirmed the problem was local to the ACM Digital Library application/service.

- After ACM applied its local fix, `https://acm.org/` returned `HTTP/1.1 200 OK` with ACM Digital Library HTML content.

- Coordinated with Uni:
