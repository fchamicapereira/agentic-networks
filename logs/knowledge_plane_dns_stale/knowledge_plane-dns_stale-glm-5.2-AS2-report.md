I observed that AS2 sits between AS1 (upstream peer) and ACM (downstream customer), with AS1 providing three reachable prefixes and ACM providing web server and management addresses. Port 53 was occupied by a stale process in an inaccessible PID namespace, returning REFUSED to all DNS queries.

I decided to install all learned routes with my loopback (154.54.1.1) as source, advertise all prefixes bidirectionally to both neighbors, and work around the port-53 conflict by running dnsmasq on 5353 with iptables NAT redirects. I also chose 4.2.2.1 as the upstream DNS forwarder since it was a known reachable AS1 prefix.

This was necessary because link-scoped addresses aren't advertised network-wide, so sourcing from loopback ensures return routability. Bidirectional advertisement was required so both neighbors could reach each other's networks through me. The port-redirect approach was low-risk and reversible since the stale process couldn't be killed from my namespace. All connectivity verified successfully: pings to all remote destinations had 0% loss, DNS resolution returned the correct answer for web.acm.example, and curl returned HTTP 200.
